扫描版 PDF / 图片 OCR —— 功能说明（2026-10-26）
==========================================================================

一句话
--------------------------------------------------------------------------
以前只能读 docx / xlsx / md / txt，"扫描件"（整页是图、没有文字层）和照片、
截图里的字一概读不到。现在：PDF 逐页判断——有文字层的直接抽（0 误差、毫秒级），
只有扫描页才渲染成图走 OCR；图片直接 OCR。认出来的文字带页码/段落定位，
和普通文档一样进检索池，后面的指令、抽取、填表全都能用。

界面入口
--------------------------------------------------------------------------
顶栏「🔎 文字识别」

  1. 点面板里的虚线框选文件，或把文件拖进去
     （.pdf / .png / .jpg / .jpeg / .bmp / .webp / .tif）
  2. 选精度：标准 200dpi（默认）/ 高清 300dpi（小字更准，慢一倍）
  3. 点「开始识别」→ 出全文 + 逐段来源（第几页 / 文字层还是 OCR / 置信度）
  4. 确认没问题，点「＋ 并入文档库」——这份文件变成"能下指令的文档"

另一条路：直接点「📥 导入文档」也可以传 PDF 和图片，后台自动 OCR 后入池，
不需要先进识别面板。两条路的区别只有一点：识别面板可以先看再决定要不要入库。

怎么判断"是不是扫描件"
--------------------------------------------------------------------------
不是看扩展名，是看**每一页**去掉空白后还剩多少字符：

  ≥ 20 字 → 这页有可用文字层 → 用 get_text("dict") 拿版面块，不 OCR
  < 20 字 → 这页是扫描图 → page.get_pixmap(dpi) 渲染 → OCR

为什么要逐页判：真实 PDF 经常是混的——前面几页电子版正文，中间夹几页扫描的
签字页/盖章页。整份判一次就会把扫描页当成"空页"悄悄丢掉（这是最常见的坑）。
验收里专门造了一份"第 1 页文字层 + 第 2 页扫描图"的混合 PDF 来盯这个点。

两个 OCR 引擎（自动选，可用 A23_OCR_ENGINE 强制指定）
--------------------------------------------------------------------------
  1) RapidOCR（PP-OCR + onnxruntime，纯 CPU 离线）—— 首选
     pip install rapidocr_onnxruntime
     中文准确率高，无尺寸限制，单页 1~2 秒

  2) Windows 自带 OCR（Windows.Media.Ocr）—— 兜底
     只要系统装了简体中文语言包就能用，零下载（agent/win_ocr.ps1）
     实测两个坑，都已处理：
       · 它按"一个字一个 word"返回，用 Line.Text 拼出来是「设 备 验 收 单」
         → 改成输出每个 word 的坐标，由 Python 按视觉间隙拼（agent/ocr.py 的 _join_parts）
       · 超过约 300 万像素会**静默返回空**（不报错、不提示）
         → 实测 3.87M 全空 / 3.13M 认一半 / 2.48M 正常，所以引擎是它时钳到 160dpi

OCR 之后怎么还原版面（agent/ocr.py）
--------------------------------------------------------------------------
  文字框 → 按中心 y 聚成"视觉行"（容差 0.6 × 行高，容忍拍照轻微倾斜）
        → 行内按 x 排序，横向间隙 > 1.25 × 行高 就切成不同"列"（表格行）
        → 行距 > 1.75 × 行高 或字号跳变 > 1.35 倍 → 断段
        → 段超过 12 行强制切开（不然一份行距均匀的公文会变成一整块，
          检索时块太大反而匹配不准）

置信度低于 0.6 的段落：结果区标黄 + 提示"建议人工复核"。
这是按项目那条底线来的——宁可留空、标出来，也不假装认对了。

复用已有结构，没有另起一套
--------------------------------------------------------------------------
  · block 结构和 txt/docx/xlsx 读取器完全一致（file / type / text / locator）
  · locator 多一种 kind：
      {"kind": "pdf_block", "page": N, "block": i, "bbox": [...]}   文字层
      {"kind": "pdf_ocr",   "page": N, "para": i, "conf": 0.93}     OCR
      {"kind": "image_para", "para": i, "conf": 0.83}               图片
  · block 多一个 source 字段（"text_layer" / "ocr"），前端据此标紫标

--------------------------------------------------------------------------
  素材                          页/张   耗时     关键串命中
  电子版-采购合同.pdf             3 页   0.04s    17/17  （全部来自文字层，0 误差）
  扫描版-采购合同.pdf             3 页   5.2s     12/13  （漏"叁拾捌万肆仟元整"→认成"参拾…"）
  混合版-统计公报.pdf            2 页   1.4s     11/11  （第1页文字层 + 第2页 OCR）

  拍照件-公告（歪0.6°+噪点）.png  1 张   1.7s      5/5   （平均置信度 0.85）

已知边界（不藏）
--------------------------------------------------------------------------
  · 手写（2026-11-03 更新）：**工整手写已支持** —— 印刷表格里的手写填空、整篇手写、
    页边横躺批注都能读（双阈值合并 + 长边不足 1700px 放大 1.5 倍 + 检测到竖向墨迹窄带时
    ±90° 补读）。4 张素材验收 16/16，关键串 90.2%→95.1%，字符 80.6%→82.7%，
    单页最慢 4.2 秒。`A23_OCR_HAND=0` 可关回旧行为。
  · 仍认不出的：**连笔草书、手写签名、印章** —— 这三类要专门的手写/签名模型，
    不是调参能解决的。另外这批结论是在"字体模拟手写"上测的，真人笔迹密度更大，
    拿到真实手写件后要复核一遍。验收记录：OCR-手写-验收-1103.txt
  · 表格里的窄列（单个数字，如"序号"列的 1/2/3）容易漏检；列宽的间隔能切出来，
    但单元格里的短数字置信度低，会被过滤
  · 中文大写数字（叁→参）、连字符（-→一）这类形近字会错，属于引擎固有误差
  · 倾斜超过 5°、分辨率低于 150dpi 的扫描件命中率明显下降
  · 兜底引擎（Windows OCR）300 万像素上限，超了会静默失败（已在代码里钳住）
  · 没有做"表格结构还原"：表格行会用「两个空格」分隔不同列，
    但不会输出标准的 table 结构（赛题没要求，且线框检测属于另一个工程量级）

怎么复跑
--------------------------------------------------------------------------
  1. 造素材：python 收尾对照/OCR-素材生成-1026.py
  2. 起服务：cd agent && python api_server.py --port 8013
  3. 接口验收：python 收尾对照/OCR-接口验收-1026.py --port 8013
  4. 真机验收：python 收尾对照/OCR-浏览器验收-1026.py --port 8013
  5. 单张排查：python agent/ocr.py 某张图.png
