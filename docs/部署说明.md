# 部署说明

> 这份文档解决的是组会 PPT 第 6 条「工程上比较糙」里缺的那半块：
> 端口怎么配、多进程怎么开、反向代理怎么加、https 怎么上、出问题看哪里。
>
> 先说明现状边界，免得照着做一半踩坑：
> - 当前是**单进程 + 线程池**（`ThreadPoolExecutor(max_workers=4)`）；
>   表格填写**同一进程内已经可以并行**（默认 2 个任务，`A23_FILL_CONCURRENCY` 调），
>   但多进程部署会变成 N × 2 并发，见第 3 节。
> - 数据库挂了服务仍能起（登录/历史降级），这是有意的设计，不是 bug。

---

## 1. 最小可用：本机启动

```bash
# 项目根目录
python agent/api_server.py --port 8000
```

Windows 上双击 `启动操作台.bat` 等价，差别是它会自动开浏览器、用指定解释器。

访问 `http://127.0.0.1:8000` → 跳转登录页 `login.html` → 选端口（user / staff / admin）。

**必须能连上 MySQL**，否则：
- 登录、操作历史、评价、聊天室不可用
- 其余功能（读文档、填表、抽取）照常

## 2. 环境变量

| 变量 | 作用 | 默认 |
|---|---|---|
| `A23_PORT` / `--port` | 监听端口 | 8000 |
| `A23_NO_BROWSER` | 置 1 则启动不开浏览器 | 未设 |
| `A23_TEMPLATE_DIR` | 模板目录（模板上传用） | `测试数据/模板表格` |
| `A23_MATCHER_DIR` | 抽取结果目录 | `matcher/` |
| `A23_OUT_DIR` | 填表成品目录 | `writer/输出/` |
| `A23_STRUCTURE_JSON` | 模板结构缓存 | `matcher/结构-模板表格.json` |
| `A23_FILL_CONCURRENCY` | 同时跑几个填表任务（进程内闸门总名额） | `2` |
| `A23_POOL_BIG_MB` | 池超过多少 MB 算"大池"（大池只允许一个填表任务跑） | `30` |
| `A23_BIG_POOL_WORKERS` | 大池上每张模板最多几列并发 | `4` |
| `A23_OCR_ENGINE` | OCR 引擎：`auto` / `rapidocr` / `winocr` | `auto` |
| `A23_OCR_HAND` | 手写增强：`auto`（默认开）/ `0`（关闭，复现旧行为） | `auto` |
| `DASHSCOPE_API_KEY` | 百炼密钥（优先级最高） | 读 `agent/llm_key.txt` |
| `ZHIPU_API_KEY` | 智谱密钥（免费档首选） | 读 `agent/llm_key.txt` |
| `SILICONFLOW_API_KEY` | 硅基流动密钥（备用） | 读 `agent/llm_key.txt` |
| `A23_PROVIDER` | 指定首选平台（`zhipu` / `siliconflow` / `dashscope` / `ollama`） | 按内置顺序自动挑 |
| `PYTHONUTF8` | 必须为 1，否则中文路径/输出会乱 | — |

生产环境请用环境变量传密钥，**不要**写进 `agent/llm_key.txt` 提交到仓库。

**模型线路要配至少两家**。免费额度会用尽（2026-11-02 就撞过一次百炼
`403 Free quota exhausted`，当时地址写死，整条抽取链直接停摆）。现在配了多家会
自动切换，但**只剩一家时等于没这层保护**。上线前跑 `python agent/llm_config.py --test`
确认至少两家 ✔。运行中看 `GET /api/llm/status` 是否已有家在冷却。

## 3. 多进程：现在不能直接开

`uvicorn --workers N` 在本项目上会出问题，原因是进程内状态：

| 状态 | 存在哪 | 多进程后果 |
|---|---|---|
| 用户会话 `sessions` | 内存 dict | 换进程就掉登录 |
| 任务队列 `jobs` | 内存 dict | 提交任务后查进度可能 404 |
| 并发闸门 `fill_gate` | 进程内加权闸门 | **不是数据错乱**（中间产物已按 `agent/jobs/<jid>/` 隔离），而是并发数变成 N × `A23_FILL_CONCURRENCY`，把模型额度瞬间打满 → 大面积 429 |
| 语义索引缓存 | 进程内单例 | 每进程各加载一次，内存 ×N（91MB 模型 + 索引） |
| 文档池 `output.json` | 共享文件 | 每个进程都会判断"池是否新鲜"，冷启动时可能同时重建（写同一个文件） |
| 聊天室心跳 | MySQL | 这个没问题 |

**结论**：要上多进程，得先把上面四项外移（Redis 或 MySQL）。
在没做之前，单进程 + 线程池是正确选择，不要强行加 `--workers`。

补一句 2026-11-03 之后的现状（以前这里写的是"填表有全局锁、多进程抢同一个中间文件"，
那已经不是事实了）：进程内的填表并发**已经打通**，两个任务同时跑实测总墙钟 30.11 秒
< 两者耗时之和 46.18 秒，产物各自独立。细节见 `收尾对照/并发与公式-1103.md`。

如果只是想让静态页更快，可以加一个 Nginx 直接托管 `web/` 下的静态文件，
只把 `/api/*` 反代给应用 —— 这是当前性价比最高的做法。

## 4. 反向代理（Nginx）

```nginx
server {
    listen 80;
    server_name your-domain.com;

    client_max_body_size 20m;          # 模板上传限制 12MB，留余量

    # 静态文件直出（web/ 目录）
    location / {
        root /path/to/研一项目/web;
        try_files $uri $uri/ @app;
    }

    # 接口交给应用
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 填表可能跑几十秒，超时要放宽，否则前端拿到 504
        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }

    location @app {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
    }
}
```

**超时是最容易踩的坑**：单文档最慢接近 90 秒，Nginx 默认 60 秒读超时会把请求掐掉，
前端表现成"一直在转圈"，日志里却是 200。必须显式放大。

## 5. HTTPS

Caddy 最省事（自动申请证书）：

```
your-domain.com {
    reverse_proxy 127.0.0.1:8000
}
```

用 Nginx 则配 `ssl_certificate` + 把 80 跳 443。
注意登录 cookie `a23_token` 在 https 下建议加 `Secure` 属性（见 `agent/auth.py`）。

## 6. 日志与排障

| 现象 | 先看哪里 |
|---|---|
| 启动就退 | 终端输出 / `agent/输出/_srv.log`，多半是依赖缺（`pip install -r requirements.txt`） |
| 页面 502 | 应用没起，或端口不对；**本机测试时注意系统代理会劫持 127.0.0.1** |
| 填表很慢 | `matcher/运行摘要.txt` 的逐列耗时；单列异常慢通常是候选块太多 |
| 抽取为空 | 该列没有抽取结果文件（`matcher/抽取结果-*.json`），先跑 `run_all.py` |
| 语义全 0 分 | `models/` 模型没下载，跑 `python agent/下载语义模型.py`；或 `sys.path` 没加 agent/ |
| 登录进不去 | MySQL 是否启动、`db_config.example.json` 是否复制成了实际配置 |
| 中文乱码 | `PYTHONUTF8=1` 没设 |
| AI 功能全哑 | `python agent/llm_config.py --test` 逐家测；`GET /api/llm/status` 看是否全部在冷却 |
| 报 403 额度用尽 | 免费额度到顶了。换一家配 key（`agent/llm_key.txt` 加一行），或把 `A23_PROVIDER` 指向别家 |
| 报 404 模型不存在 | 各平台模型名不一样，改 `llm_config.py` 里对应的 `model` |
| 免费档报 429 | 单并发的平台被并发打了。代码里有信号量排队，还报就说明同一时刻有多进程在跑 |

日志位置：
- 服务输出：启动窗口（或自己重定向的文件）
- 运行日志：`运行日志.txt`
- 抽取摘要：`matcher/运行摘要.txt`
- 填表报告：`writer/输出/填表报告-*.txt`

## 附：为什么现在不做成多进程

写清楚理由，比留一个"待优化"更诚实：

单进程跑得动当前规模（4 个线程并发处理不同用户），而多进程要改四处状态管理，
改动面比收益大。真正的瓶颈不在并发数，在**单文档耗时**（受模型调用轮数影响）。
所以优化顺序是：先把单文档时间压下来，再考虑横向扩。

如果将来要上多进程，最小改动路径：
1. `sessions` → MySQL 表（表结构已有 `sessions`，改成读写库即可）
2. `jobs` → MySQL 或 Redis
3. `fill_gate` → 跨进程配额（Redis 计数或网关限流；中间产物已经隔离，不用再动）
4. 语义索引 → 进程外服务或共享内存
5. 文档池重建 → 加文件锁，避免冷启动时多进程同时重写 `output.json`
